## Our Commitment
We are committed to creating a collaborative, respectful, and productive team environment where all members can contribute effectively to the project.

## Communication Guidelines

### Meeting Schedule
- **Weekly Team Meetings**: [monday 2pm thursday 2pm  friday 2pm]
- **Location**: [In Person/MS Teams ]
- **Attendance**: All members expected to attend. If unable, notify team 24 hours in advance.

### Communication Channels
- **Primary**: [WhatsApp/MS teams]
- **Code Reviews**: GitHub pull requests
- **Documentation**: GitHub repository

### Response Times
- Messages during working hours (9 AM - 9 PM): Within 4 hours
- Pull request reviews: Within 24 hours
- Meeting invites: Respond within 12 hours

## Work Distribution

### Task Allocation
- Tasks will be assigned fairly based on skills and availability
- Each member should contribute equally (~25% of total work)
- If struggling with a task, communicate early to get help

### Responsibilities
- **Code Quality**: Write clean, commented, and tested code
- **Deadlines**: Complete assigned tasks by agreed deadlines
- **Documentation**: Document your code and design decisions
- **Reviews**: Actively participate in code reviews

## GitHub Workflow

### Branching Strategy
- `main` - Production-ready code only
- `develop` - Integration branch for features
- `feature/[name]` - Individual feature branches
- Example: `feature/price-fetcher`, `feature/database-setup`

### Commit Guidelines
- Write clear commit messages
- Format: `[type]: description`
- Types: `feat`, `fix`, `docs`, `refactor`, `test`
- Example: `feat: add stock price API integration`

### Pull Request Process
1. Create feature branch from `develop`
2. Make changes and commit
3. Push to GitHub and create pull request
4. Request review from at least one team member
5. Address review comments
6. Merge only after approval

## Conflict Resolution
1. **Discussion First**: Try to resolve through team discussion
2. **Voting**: If no consensus, majority vote (3/4)
3. **Escalation**: If serious issues arise, consult module instructor
4. **Respect**: Disagree professionally, no personal attacks

## Consequences
- **First Warning**: Reminder of commitments
- **Second Warning**: Team meeting to discuss issues
- **Persistent Issues**: Report to module instructor

## Quality Standards
- All code must compile without errors
- Code must follow Java naming conventions
- Methods should be documented with JavaDoc
- Test coverage for critical functionality
- No committing directly to `main` branch

## Meeting Protocols
- **Agenda**: Shared 24 hours before meeting
- **Minutes**: Recorded and shared after each meeting
- **Action Items**: Clear ownership and deadlines
- **Punctuality**: Start on time, max 5 minutes grace period

## Decision Making
- **Technical Decisions**: Discussed and agreed by majority
- **Architecture Changes**: Full team agreement required
- **Task Reallocation**: Team consensus needed

## Agreement
By contributing to this project, all team members agree to abide by this Code of Conduct and are fully made aware of 
the penalties and consequences if not adhered to
